# Changelog

All notable changes to `ranetrace-laravel` will be documented in this file.

This file starts at 1.0.0. The package was re-versioned to share a major with `ranetrace/ranetrace-php`, which it now requires; the releases before that point are not recorded here, the git history is the record for those.

## [Unreleased]

### Added
- **An opt-in human-verification beacon for website analytics, so a visit can be counted only when a real browser rendered it.** Every other filter on the capture path reads what a request claims about itself, which an HTTP client can lie about; the beacon asks the other side to prove it. Turn it on with `RANETRACE_WEBSITE_ANALYTICS_BEACON_ENABLED=true` and keep `@ranetraceErrorTracking` before `</body>`: that directive now renders the beacon as well as the JavaScript error script, so a layout that already carries it needs nothing but the env var, and the two stay independently gated. The mechanism is one delayed job and one cache key. The capture middleware mints a token for the view, hands it to the page and dispatches the page visit job delayed by `RANETRACE_WEBSITE_ANALYTICS_BEACON_WAIT_SECONDS` (default 15). In the browser the beacon starts at once rather than on `load`: after one painted animation frame and `RANETRACE_WEBSITE_ANALYTICS_BEACON_DELAY_MS` (default 0, since a delay is a minimum time on page) it checks the page is visible and posts that one token to the new `POST ranetrace/analytics/verify` route (named `ranetrace.analytics.verify`, rate limited by `RANETRACE_WEBSITE_ANALYTICS_BEACON_THROTTLE`, default `120,1`). The endpoint only leaves a mark in Ranetrace's own cache store; when the job runs it reads that mark and the visit ships with the new `verified_human` field, true or false. Nothing is parked and nothing is swept, so a browser that never answers costs a flag rather than a visit. The route is mounted whenever analytics is enabled and answers 403 while the beacon is off, so a beacon from an already-served page gets a clean refusal instead of a 404. A page that is hidden when the beacon is due (a background tab, a prerender) is waited on and posts once it is shown, and leaving a page that was visible posts too, so a configured delay never drops a visitor who leaves before it elapses; a page opened in a background tab and first looked at after the wait is still reported unverified, because its visit has already been sent. **It requires a real queue connection**: a connection that runs jobs at once (`sync`, `deferred` or `background`) ignores the delay, and `RANETRACE_WEBSITE_ANALYTICS_QUEUE=false` sends the visit before the response leaves the server, so in either case there is nothing to wait for, and such a visit is sent with no `verified_human` field at all rather than a false one, from a page that carries no beacon. **Keep it off behind a full-page cache** (Cloudflare cache-everything, a static export): the token is printed into the HTML, so a cached page hands one token to every visitor. The privacy promise changes with it and now reads: no cookies, no fingerprinting, no consent banner, and an optional beacon that sends one opaque token and nothing else

### Changed
- **The Boost guideline and skills now say what the code does.** Boost copies this text into every consuming application, and an agent follows it literally, so each claim the code contradicted was an instruction to get something wrong. The guideline now says that `ranetrace:work` has to be scheduled, with the scheduler line and a pointer to the `ranetrace-worker` skill, because nothing leaves the application until it runs; it names `RANETRACE_KEY` as the setting that gates capture and says `RANETRACE_ENABLED` defaults to on; and it drops the middle one of three copies of the exception-wiring warning. The skills drop the retired 409 `MONITOR_DISABLED` answer (a disabled monitor is a plain error from the hosted tool), say that the MCP 401 arrives before any tool runs, stop quoting a tool description that has since changed, say that an invalid event name throws (on every call, see Fixed), stop promising a country code that is never captured, call the one navigation breadcrumb what it is (the page load), and say that on a connection that runs jobs at once (`QUEUE_CONNECTION=sync`, `deferred` or `background`) or with `RANETRACE_WEBSITE_ANALYTICS_QUEUE=false` a visit is sent with no `verified_human` field at all, so the beacon only verifies anything on a real queue connection
- **The shared browser capture script is minified upstream, so `@ranetraceErrorTracking` ships about 9 KB less to every page that renders it.** The script drops from about 13.4 KB to about 4.3 KB, and from 4.0 KB to 1.7 KB over the wire; with this package's runtime config substituted, what lands on the page goes from 13925 to 4812 bytes, 4197 to 1974 gzipped. It is inlined into every page view of every site that installs the package, so its comments and indentation were being downloaded by every visitor on the critical path of a page they were waiting for. **Behaviour is unchanged**: the same listeners, the same `X-CSRF-TOKEN` header, the same breadcrumbs, deduplication and `window.Ranetrace` API, the same config values out of `config/ranetrace.php`, the same route and the same nonce attribute. Nothing in this package's code, config, env vars or routes moved, and nothing has to be installed: `ranetrace/ranetrace-php` commits the minified file and ships it in its Composer package, because Composer runs no JavaScript toolchain and no consumer may need node. The change arrives with the `ranetrace/ranetrace-php` release that carries it, so until this package's requirement is bumped the script renders unminified as before. The one thing to know is that **every local variable and function in the script is renamed**, so anything of yours that recognised it by one of those names, or by a phrase from its header comment such as `Ranetrace JavaScript Error Tracking`, has to key on something minification keeps: a string literal, a property name, a config key, or `window.Ranetrace.captureError`
- The tests that find the error script are re-keyed on exactly that. Four assertions looked for `Ranetrace JavaScript Error Tracking`, which only ever existed in the script's header comment, and the config block was read with a `const config = ` regex whose variable name minification shortens to a single letter. The marker is `window.Ranetrace.captureError` now, the CSRF assertion looks for the header name rather than for the line that sets it, and the config literal is located by the script around it rather than by that name, so each one holds against the minified and the unminified script alike. One further guard is added and skips itself while the resolved `ranetrace/ranetrace-php` predates the minified twin: that the directive then ships no comment at all, from either view
- **The human-verification beacon ships about 0.9 KB less to every page that renders it, and behaves exactly as before.** Its JavaScript comments were inline in the `<script>` element, so the notes explaining the beacon were downloaded by every visitor of every site that installs the package, on the critical path of a page they are waiting for. They are Blade comments now: the compiler removes them before anything renders, so they stay in the source and leave the page. The rendered beacon goes from 2368 to 1469 bytes, and `@ranetraceErrorTracking` with both features on from 16279 to 15380. No line of the beacon's logic, its config, its route or its timing moved. Three tests render the directive's views and fail on any comment that reaches the output, including a Blade comment whose braces were mangled on the way in, which renders as page text. The shared browser capture script is not touched by this move: it is a JavaScript file in `ranetrace/ranetrace-php` rather than a Blade template, so its comments cannot be compiled away, and the figures above were measured while it still carried them. The guard pins that this package's wrapper adds none of its own around it. The entry above takes the same weight off that script by the other route, minifying it upstream
- **The Boost guideline is about 4 KB lighter, and nothing it said is lost.** Boost copies the guideline into the CLAUDE.md of every application that installs the package, so an agent reads it on every turn of every session, while a skill is read only when an agent activates it. The guideline goes from 10230 to 6206 bytes. Its MCP section, 4.9 KB of tool catalog, OAuth flow, approval screen, retired tokens and monitor tools, is one paragraph now: the server is hosted, an OAuth client connects to `https://api.ranetrace.com/mcp`, the user picks one website and read or write at the approval screen, no token goes in `.env` and `RANETRACE_MCP_TOKEN` is a retired setup, and for everything else the agent activates the `ranetrace-error-tracking` skill. The Middleware section keeps the privacy promise and the two beacon constraints (a real queue connection, off behind a full-page cache) and points at the `ranetrace-analytics` skill for how the beacon works. Both skills already held every fact that left the guideline, which was checked sentence by sentence and not by keyword. What stays always-on is what prevents a wrong action without anyone asking: the ingest key is not an MCP credential, and no MCP credential goes in `.env`. Because a skill's description is the only part an agent sees before it loads one, the error-tracking description now names the hosted MCP server, connecting over OAuth, the `search_tools` and `execute_tools` flow, the monitor verdicts and the notification rules, and the analytics description names the beacon. The error-tracking skill also states the kebab-case wire spelling once, ahead of its tool tables, with `search-errors-tool` and `get-monitor-status-tool` as examples, where it used to appear only beside the write flow. Three tests keep it so: every skill the guideline tells an agent to activate ships under that name, the error-tracking description keeps the words the MCP pointer relies on, and the guideline stays under 7 KB. Documentation only; no code, config value, env var or route moved
- **Two hosted MCP tools gained parameters, and the Boost guideline and the error-tracking skill now say so.** `search-errors-tool` takes a free-text `query`: a case-insensitive substring, at most 200 characters, matched against the error message (for a PHP error the message of its latest occurrence), the error type and the file, and for JavaScript errors the page URL too, with `%` and `_` read as literal characters. It combines with every other filter, so an agent finds the errors that mention a phrase or come from one class or file in one call instead of paging through results. `get-broken-links-tool` no longer stops at a capped list of 100: it lists 100 links per call and takes `status_code` (0 for a link that gave no HTTP answer), `source_page` and `cursor`, so every broken link of an audit can be walked page by page and narrowed by status or by the page it was found on. The filters narrow the list only; the verdict and the counts keep describing the whole audit. The other monitor tools stay parameterless, and the guideline's "none takes parameters" sentence now names broken links as the one exception. Documentation only; the tools live on the hosted server, so no code, config value, env var or route in this package moved
- **The hosted MCP server keeps its state-changing tools in a searchable catalog rather than in `tools/list`, and the Boost guideline and the error-tracking skill now describe that path.** The read tools (error investigation, note reads, the monitor verdicts, the notification-rule read) are listed directly and are called by name as before. Everything that changes something (the error state tools, their bulk variants, note create, create-many, update and delete, and the notification-rule update) is reached through two meta tools that a write-enabled connection lists next to the reads: `search_tools`, which takes a `query` and an optional `limit` of 1 to 50, browses the whole catalog on an empty query, and answers each match with its name, description and input schema; and `execute_tools`, which takes `calls`, at most ten of them, and runs them in order, stopping at the first error. A catalogued tool cannot be called by its own name through `tools/call`, which answers not found, so a state change is search first and then execute, and `execute_tools` re-checks the write permission on the way through. Tool names did not change; the wire spelling is the kebab-case one (`resolve-error-tool`), which is what `search_tools` answers with and `execute_tools` expects. A read-only connection is now described exactly: it lists the read tools and nothing else, no write tools and no meta tools. The guideline carries the shape and a two-line snippet, the skill adds a worked example that resolves an error and marks every tool table as listed or catalogued. Documentation only; no code, config value, env var or route moved
- The error-tracking skill says that the hosted MCP server's six note tools take a required `type` (`php`, or `javascript` or `js`), the same argument the error state tools take, so notes reach JavaScript errors too; before, a `jserr_` id silently reached the PHP error with the same number. Documentation only; the tools live on the hosted server, so no code, config value, env var or route in this package moved
- The Boost guideline's MCP section says the same monitor sentence as the hosted server's own instructions (what `get-monitor-status-tool` answers, what the per-monitor tools add, verdict before numbers), and the guideline and the error-tracking skill drop their em-dashes, which the house writing rule keeps out of anything the package says
- The six Boost skills no longer carry em-dashes in their prose, which finishes the sweep the entry above left open. The option and facade bullets in the JavaScript errors, logging and event tracking skills now read as `name`: description, the joined clauses in the endpoint, self-logging, scrubbing, log driver, worker cache store and captured-request sentences became a colon, a comma or a new sentence, and the batch cache comment in the worker skill's config example reads ", never `array`" the way the guideline's pitfall does. No option, env var, route name, signature or fact changed; these skills ship into every consuming project, so the house writing rule applies to them the same way it applies to the guideline
- The README no longer carries em-dashes in its prose either, which finishes the sweep for everything the package ships to consumers. The confirmation after the exception-handler wiring, the event tracking sentence and the diagnostics dashboard's graceful-degradation sentence became a colon, the `ranetrace:status` description a comma, and the comment in the logging stack example reads `// config/logging.php: example stacked channel`. No code, config value, env var, command or fact changed
- The three sentences the package speaks in its own voice no longer carry em-dashes either, which finishes the sweep for everything a consumer actually reads. The dashboard's volatile-cache-driver advice reads "Fine locally, but buffers/pauses will not survive in production. Use a durable store there.", the `ranetrace:work` failure line reads "Ranetrace: ranetrace:work could not run. Is the cache/queue backend available? See the ranetrace_internal log.", and the buffer-overflow warning on the internal channel reads "Ranetrace buffer overflow, oldest items dropped". Each of the three is pinned by its own test, so the dash cannot come back unnoticed. The PHPDoc and inline comments under `src/` were swept in the same pass: 72 dashes across 25 files became a comma, a colon, parentheses where a dash pair framed an aside, or a new sentence, with every fact, name, path, env var and `{@see}` reference kept and no code touched. Nothing behaves differently; the only shipped strings that moved are the three above, so anything grepping the internal log for the old overflow wording needs updating
- The diagnostics dashboard no longer carries em-dashes in what it renders, which finishes the sweep for the last surface a consumer reads. The page title is "Ranetrace diagnostics" and the forbidden page's is "Ranetrace diagnostics: Forbidden", the stalled-buffer warning reads "Drain stalled: buffered items aren't being sent.", the log panel is titled "Internal log: warnings and errors" and its empty state reads "No recent warnings or errors, or the internal log file isn’t present yet.", the failed-jobs warning reads "High failure rate. Check the internal log and the failed_jobs table.", and the three pause reasons read "Payload too large: client bug, investigate", "Validation failed: schema drift" and "Rate limited, auto-resumes". The bare dash the configuration and environment panels render for a value they do not have stays, being a symbol rather than prose. Two tests pin the new wordings and sweep the whole rendered page for the character, so it cannot come back unnoticed. The comments under `tests/` and the dashboard's own script and stylesheet were swept in the same pass: 41 dashes across 22 files became a comma, a colon, parentheses where a dash pair framed an aside, or a new sentence, with every fact, name and path kept. Nothing behaves differently, and no markup, class name, route or config value moved
- **Website analytics counts fewer visits from this release, and what stops being counted is bots, not visitors.** Two server-side filters were added to the capture path. The human-probability gate is now a configurable minimum score and defaults to 70, where the classification check it replaces let everything from 50 upwards through: set `RANETRACE_WEBSITE_ANALYTICS_MIN_HUMAN_SCORE=50` to keep the old behaviour, and lowering it is also the answer if legitimate visitors go missing (uncommon browsers, privacy proxies that strip headers). And a request whose user agent claims Chrome or Edge 100 or newer while carrying no `Sec-Fetch-Site`, `Sec-Fetch-Mode`, `Sec-Fetch-Dest` or `Sec-CH-UA` header is now rejected as a spoofed HTTP client: every real Chromium build sends at least one of those on a navigation, so their total absence contradicts the user agent that claims them. `RANETRACE_WEBSITE_ANALYTICS_REQUIRE_CLIENT_HINTS=false` switches that check off and `RANETRACE_WEBSITE_ANALYTICS_MODERN_BROWSER_MIN_VERSION` moves the version floor; older Chromium builds and non-Chromium browsers are never touched by it. A `Sec-CH-UA` header additionally adds 10 points to the human-probability score, being awkward for a simple HTTP client to forge consistently with the user agent it claims. Expect a visible step down in visits on the day of the upgrade, followed by a lower but truer baseline
- **MCP tokens are retired.** The static per-website token is no longer accepted by the hosted MCP server: a client still sending one as `Authorization: Bearer`, or sending the ingest key `RANETRACE_KEY` there, gets a 401 with `error_code: MCP_OAUTH_REQUIRED` and a message telling it to remove the header and reconnect over OAuth. The old 403 `MCP_TOKEN_REQUIRED` answer no longer exists. The README, the Boost guideline and the error-tracking skill describe the OAuth connection as the only MCP credential and no longer show the bearer-header commands
- The website's `/mcp` page is gone. The instructions for connecting an agent now live on the account's agent connections page in Ranetrace, at `/user/profile/connections`, next to the list of approved connections
- The `ApiKeyCheck` hint, the `ranetrace:status` recommendation and the dashboard status comment no longer speak of "a separate token" for the MCP tools; they say the MCP tools use an OAuth connection held by the MCP client. Nothing about `RANETRACE_KEY` changes: it is the ingest key and belongs on every server

### Fixed
- Website analytics counts people behind one shared IP separately again. The capture throttle kept one visit per IP and path per `RANETRACE_WEBSITE_ANALYTICS_THROTTLE_SECONDS`, so two people in one office or on one mobile carrier's NAT opening the same page within the window counted as one. The throttle key now includes the visitor's salted user-agent hash as well: a reload by the same browser still counts once
- An invalid event name passed to `Ranetrace::trackEvent()` now throws its `InvalidArgumentException` wherever it is called, so it fails in development instead of first in production. The name was checked only after the capture gate, so with no `RANETRACE_KEY`, events off or the master switch off (the usual state of a development machine) a bad name passed silently; `RanetraceEvents::custom()` already checked before the gate. An application that has been passing bad names with capture off will now see the exception locally. `validate: false` still skips the check
- `@ranetraceErrorTracking` no longer breaks the page it is on while `RANETRACE_ENABLED=false` and `RANETRACE_JAVASCRIPT_ERRORS_ENABLED=true`. The relay route the JavaScript error script posts to is mounted only with the master switch on, but the view rendered the script on the feature flag alone and called `route()` for that relay, so every page carrying the directive failed with a `RouteNotFoundException` (a 500) instead of rendering. The script now renders on the same condition the route is mounted on, and the service provider and the view read it from one method, `JavaScriptErrorController::isMounted()`, so the two cannot drift apart again. The beacon half needed no change: its token comes only from the capture middleware, which does not run with the master switch off

## [1.1.1] - 2026-08-27

### Removed
- **The local MCP server, its 31 tools and the `ranetrace.mcp` config block are gone.** Ranetrace hosts the same 31 tools itself, over Streamable HTTP at `https://api.ranetrace.com/mcp`, so nothing has to run in your application and nothing has to be installed for it. Moving over is two steps and touches only your MCP client: create a token on your website's `/mcp` page in Ranetrace, then add the server with `claude mcp add --transport http ranetrace https://api.ranetrace.com/mcp --header "Authorization: Bearer <token>"`, or the equivalent `mcpServers` entry with `"type": "http"`, the same URL and the same header. Tool names, parameters and output are unchanged, so nothing an agent already knows has to change. `RANETRACE_MCP_ENABLED` and `RANETRACE_MCP_TOKEN` are no longer read anywhere: drop them from `.env`, and drop `laravel/mcp` from your application if nothing else needs it. The 1.1.0 entry below promised this removal in the next major release; it lands here, in a patch release, by the maintainer's deliberate choice as the package's only consumer
- `RanetraceApiClient`'s read methods, which existed only to serve those tools: the error, note and error-state calls and the seven monitor reads, along with the retry helper and the `MCP_TOKEN_REQUIRED` message handling they used. The five ingest batch methods and everything the batch worker touches are unchanged
- The diagnostics dashboard, `ranetrace:status` and `ranetrace:test` no longer report an MCP token or an MCP server surface. The token belongs with the MCP client now, so this application has nothing left to say about it. The two credentials stay as distinct as they were: `RANETRACE_KEY` writes captured telemetry in and belongs on every server, the MCP token reads data back out and belongs with the client

## [1.1.0] - 2026-08-27

### Deprecated
- **The local MCP server is deprecated and will be removed in the next major release.** Ranetrace now hosts the same 31 tools itself, over Streamable HTTP at `https://api.ranetrace.com/mcp`, authenticated with the same MCP token sent as an `Authorization: Bearer` header. Nothing has to run in your application, and `RANETRACE_MCP_TOKEN` no longer has to sit in `.env`. Move a client over by replacing its server entry with `claude mcp add --transport http ranetrace https://api.ranetrace.com/mcp --header "Authorization: Bearer <token>"`, or the equivalent `mcpServers` block with `"type": "http"`. Tool names, parameters and output are unchanged, so nothing an agent already knows has to change. Nothing is removed in this release: `php artisan mcp:start ranetrace` and `config('ranetrace.mcp')` keep working exactly as before. The `/mcp` page in Ranetrace now issues a named token per agent, so each client can be revoked on its own

### Changed
- `RanetraceApiClient` no longer hardcodes the API base URL. It resolves `base_url` through the shared core config, exactly as `ranetrace/ranetrace-php`'s client does — same fallback to the built-in default, same trailing-slash trim — so both SDKs address the same host and a non-production API can be pointed at without editing the package. The resolved value covers every request the client sends: the five ingest batch endpoints and all MCP read calls. Nothing changes for an application that configures nothing: the default is the same URL as before

## [1.0.0] - 2026-08-21

### Added
- New default `excluded_paths` entries: `up`, `sanctum`, `_ignition` (note: apps that already published `config/ranetrace.php` keep their frozen list and must add these manually)

### Changed
- **The four wire payload shapes, the endpoint table and the response matrix now come from `ranetrace/ranetrace-php`.** This package no longer describes any of them itself: the error, log, event and JavaScript-error items are composed by the shared builders, batches are addressed from the shared endpoint table, and every per-status decision (re-buffer, pause scope, pause length, drop, the `Retry-After` substitute, the 200 counters and `unprocessed_indexes`) is read from the shared response policy. What each host puts on the wire is unchanged; what changed is that there is now one description of it instead of two. Two descriptions of a strictly field-matched payload eventually disagree, and the disagreement surfaces as a backend 422 that discards a batch of up to 1000 items and pauses the type for 15 minutes, not as a failing test in either repo
- This package provides CONTEXT to those builders instead of building payloads itself: the `Request`'s headers, full URL and method, `runningInConsole()`, the Artisan command line, the authenticated user, the Carbon clock, and the secret-bearing path segments its ROUTER resolves. Everything Laravel alone can answer stays here; every cap, allowlist, truncation rule and key order is now shared. `Ranetrace\Laravel\Support\CoreConfig` is the seam: `Ranetrace\Php\Config`'s key set already mirrors `config/ranetrace.php`, so the published config goes straight in with the environment, project root, framework identity and user resolver added
- **Redaction, byte budgeting and fingerprint derivation now come from `ranetrace/ranetrace-php` too.** They were the last duplicated utilities: two copies of a 500-line scrubber, two of the byte sizer, two of the fingerprint generator, each guarded only by a docblock asking the next maintainer not to let them drift. They had drifted already, which is the point. `Ranetrace\Laravel\Support\Core` is the seam that pairs the shared classes with this application's config and diagnostics
- The router knowledge that made this package's scrubber irreplaceable is now a seam in the shared one rather than a second implementation. `SecretScrubber::scrubDeep()` and `scrubUrlPath()` accept a callable for `$sensitiveValues`, and `RouteSecretResolver::resolver()` is what this package passes: each URL found in free-form data (breadcrumbs, log context, event properties) is matched against the route table on its own, exactly as before, because those URLs describe requests other than the one being handled. Where the current request's own route is also known (the event `url`, the error `url`), its values travel alongside the per-URL lookup rather than instead of it: `forUrl()` can only match GET routes, and a capture during a POST to `invitations/{token}/accept` must not lose that. A redactor's answers compose, so the union can only redact more
- Transport and buffering stay this package's own. The queued capture jobs, the cache-backed buffer and pause manager, and the batch job's 60/300/900s retry envelope are unchanged: only the SHAPES and the POLICY moved. A transient failure (network, 5xx, unnamed status) still spends the retry envelope before pausing, where the PHP SDK's file-based worker pauses on the spot — the shared policy names that difference explicitly (`BatchOutcome::$transient`) and both land on the same 15-minute pause, which is the half the wire contract fixes
- `RanetraceApiClient` gained `sendBatchOfType(string $type, array $items)`, which resolves the path, wrapper key, User-Agent and timeout from the shared table. The five `send*Batch()` methods now delegate to it and are otherwise unchanged. The protected `sendBatch()` signature changed from four strings to one `Ranetrace\Php\Http\Endpoint`
- `SendBatchToRanetraceJob`'s eight `handle*Response()` methods and `reAddUnprocessedItemsToBuffer()` are gone, replaced by the shared decision plus this package's own handling of it. The internal-log wording, levels and context keys are unchanged, with one exception: a failure whose `error.message` is an empty string now logs the generic fallback (`Unauthorized`, `Forbidden`, …) instead of the empty string. Diagnostics only; nothing on the wire
- Two edges of the error payload changed, both toward what the contract already allowed. A request that carries no headers at all now sends `headers: null` rather than `{}` (the field is typed as an object on the wire, and `json_encode([])` is a JSON array). An `Authenticatable` whose `getAuthIdentifier()` returns null now sends `user: null` rather than `{"id": null, "email": null}`, which is a state Laravel's own auth does not produce
- Three edges of the JavaScript-error payload are normalised the way the PHP SDK's relay already normalised them, all in the safe direction and all unreachable from the bundled capture script, which always sends these correctly: an explicit `"type": null` now ships as `"Error"` instead of null; `line` and `column` sent as numeric strings ship as integers; and `max_breadcrumbs: 0` now keeps no breadcrumbs instead of keeping all of them (`array_slice($crumbs, -0)` is `array_slice($crumbs, 0)`)
- **Website-analytics visitor and session hashes are re-keyed once, on upgrade.** The fingerprint salt used to fall back to `app.key` when `ranetrace.fingerprint_salt` was unset; it now falls back to `ranetrace.key`, matching the PHP SDK, so the same visitor hashes the same way whichever SDK observed them. Every `user_agent_hash` and `session_id_hash` therefore changes value on the release that carries this. The hashes are one-way and rotate daily by design, so nothing is lost and nothing needs migrating, but the day of the upgrade shows a **one-off spike in unique visitors**: the same person is counted once under the old salt and once under the new one. It settles by itself the next day. Set `RANETRACE_FINGERPRINT_SALT` to your current `APP_KEY` before deploying to avoid the blip entirely
- `JavaScriptErrorController::DEFAULT_IGNORED_ERRORS` reads `Ranetrace\Php\Config::DEFAULT_IGNORED_JAVASCRIPT_ERRORS` instead of repeating the same fifteen strings. The browser filters on that list before posting and this endpoint filters on it again, so two copies of it were two chances for the browser to send noise the endpoint would have dropped, or the reverse. The values are unchanged
- The free-form string scrubber (`scrubString`, applied to exception messages, stack traces, log messages and the Artisan command line) is no longer super-linear on long runs of word characters. It used to reach PCRE's backtrack limit on such inputs, at which point the whole value was redacted wholesale rather than pair by pair: correct, but lossy, and precisely on the long inputs most likely to hold something worth reading. The fix is in `ranetrace/ranetrace-php`; see its changelog for the pattern change. Fail-closed behaviour on a genuine PCRE give-up is unchanged
- **The package now requires `ranetrace/ranetrace-php` `^1.0`.** It was a dev dependency, used only so the two SDKs could test against the same wire-contract artifact; it is a runtime dependency now, because the browser capture script lives there and this package renders it from there
- The browser capture script is no longer duplicated in `resources/views/error-tracker.blade.php`. Some 370 lines of it were byte-identical to `ranetrace/ranetrace-php`'s `resources/js/error-tracker.js`, and each SDK's relay validates exactly what its own copy sent, so a fix applied to one silently stranded the other and nothing failed until a browser posted a shape the other relay did not accept. The view is now a wrapper around `Ranetrace\Php\JavaScript\CaptureScript::withConfig()` carrying only what Laravel supplies: the mounted route, the `config/ranetrace.php` values, the CSRF token and the Vite CSP nonce. The rendered output is unchanged in behaviour — same config values, same `X-CSRF-TOKEN` header, same nonce attribute — though not byte-for-byte, since the config block is now a JSON object literal (a sample rate of `1` reads as `1.0`) and the shared script carries a longer header comment
- The snippet sends `X-CSRF-TOKEN` only when there is a token to send. It previously sent the header unconditionally, so a page rendered with no session started sent an empty one; such a request fails the CSRF check either way
- Log records name their framework generically: the `extra` metadata attached to every shipped log is now `environment`, `php_version`, `framework` (`laravel`) and `framework_version`, replacing the `laravel_version` key. This matches the error payload's earlier move and the framework-agnostic PHP SDK's vocabulary, so the two SDKs describe the same host the same way. The backend accepts both spellings today; the legacy one is scheduled for removal once deployed SDKs have moved over
- Website analytics reports the request `path` decoded, so every spelling of one page (`/login`, `/%6Cogin`) is a single entry instead of an attacker-chosen supply of distinct ones. Redaction still runs on the raw path before decoding, because the values resolved from the route are compared against rawurldecoded segments. Data collected before this release keeps its original encoding, so the two are not directly comparable for pages that were ever requested encoded. The `url` field is unchanged and stays encoded — decoding a whole URL would corrupt any query value containing an encoded `&` or `=`
- MCP tool results changed shape: untrusted values are quoted JSON literals, so `**Message:** Database connection failed` now reads `**Message:** "Database connection failed"`, and a PHP exception class renders with doubled backslashes. Note bodies and the `error-stats` top-error list changed the same way, and note bodies are additionally wrapped in a fenced block. Anything parsing that output needs updating; agents reading it are unaffected
- Error payloads now send the generic `framework: laravel` + `framework_version` pair instead of the legacy `laravel_version` field (item goes from 18 to 19 keys). Requires a backend that accepts the generic pair (app commit `0d93eae0` or later); see the wire contract in `ranetrace/ranetrace-php` (`contract/items/errors.json` and `contract/CHANGELOG.md`)
- Refactored package to use native Laravel service provider instead of Spatie Laravel Package Tools
- Removed `spatie/laravel-package-tools` dependency
- Service provider now extends `Illuminate\Support\ServiceProvider` directly
- All functionality preserved (config publishing, commands registration, middleware, singleton bindings, log driver)

### Removed
- `Ranetrace\Laravel\Utilities\DataSanitizer`. Its only callers were the log handler and the JavaScript error controller, both of which now shape their items through the shared builders, which use `Ranetrace\Php\Support\DataSanitizer` — a verbatim port with the same markers and the same depth ceiling
- `Ranetrace\Laravel\Utilities\SecretScrubber`, `Ranetrace\Laravel\Utilities\PayloadSizer` and `Ranetrace\Laravel\Analytics\FingerprintGenerator`, replaced by `Ranetrace\Php\Support\SecretScrubber`, `Ranetrace\Php\Support\PayloadSizer` and `Ranetrace\Php\Support\FingerprintGenerator`. The shared classes are instances rather than static facades, so an application calling one of these directly resolves it through `Ranetrace\Laravel\Support\Core::scrubber()` / `::fingerprints()`, which pairs it with `config/ranetrace.php`. `RouteSecretResolver` stays: it is the Laravel half, and the only part that needed a router
- `Ranetrace\Laravel\Utilities\CoreScrubber`, the temporary bridge that let the shared builders redact through this package's scrubber while the two were still separate implementations

### Fixed
- Website analytics no longer counts non-GET requests as page visits (form submissions, `broadcasting/auth`, Livewire/Inertia XHR)
- Requests carrying the `X-Livewire` header are always skipped — Livewire 4 serves its endpoint from `/livewire-{hash}/update` (hash derived from `APP_KEY`), which the static `livewire` excluded-path entry can no longer match
- The package no longer tracks visits to its own diagnostics dashboard; the skip follows the configured `dashboard.path`/`dashboard.domain` instead of a hardcoded prefix
- A JavaScript error payload carrying an explicit `breadcrumbs: null` no longer raises a `TypeError` behind a 500 and an internal-log line. The rule permits null, and `Request::input()`'s default only applies to a missing key, not a stored one — Laravel's `ConvertEmptyStringsToNull` also turns a form-encoded `breadcrumbs=` into exactly that
- Campaign parameters are read as bounded strings, so `?utm_source[]=x` no longer puts an array into a `string|null` field. A single crafted page view could otherwise get the whole batch rejected as schema-violating, dropping up to 1000 legitimate visits and pausing page-visit capture for 15 minutes

### Security
- Telemetry now redacts sensitive route-parameter values from URL **path** segments, not just query strings. A segment is treated as secret when the route that owns it names it sensitively — e.g. the `{token}` of `reset-password/{token}`, the `{hash}` of `email/verify/{id}/{hash}`, or the binding field of a custom-key binding such as `{invitation:token}`. Those pages remain tracked (as e.g. `/reset-password/[REDACTED]`), so the page-view signal is preserved. This is best-effort by design: the route definition is the only available oracle for which segment holds a secret, so a parameter named `{code}` or `{t}` cannot be recognised — add such names to `ranetrace.scrubbing.extra_keys` to cover them
- Path redaction is applied everywhere a URL leaves the host, not only to the page-visit `url`/`path`: the visit `referrer`, the `Referer` header captured on error payloads, the error and event `url`, and the page URL reported by the JavaScript error snippet. The referrer cases matter on their own — a same-origin navigation sends the full previous URL by default, so a live reset token would otherwise arrive one page-view after `/reset-password/{token}` was itself redacted. URLs that did not originate from the current request are matched against the application's own routes to find their sensitive segments
- URL values inside breadcrumbs and log context are now recognised by their **shape** rather than by an `http(s)://` prefix, and both halves are scrubbed rather than only the query. Previously a relative URL passed through untouched, so a signed download link recorded as `/exports/42/download?expires=…&signature=…` shipped its signature, and a reset link copied into a navigation breadcrumb shipped its live `{token}` segment even though the identical URL in the top-level `url` field was redacted in both halves. The shape test is deliberately strict — no whitespace, none of the characters that only turn up in prose, JSON and code, and a query that is a run of `key=value` pairs — because the redaction rewrites everything from the first `?`, and a looser test would truncate a JSON log-context payload mid-structure. A value that fails the test is left byte-for-byte alone. Path resolution is skipped entirely for applications that define no secret-bearing route, decided once per scrub rather than per string
- The JavaScript error `message` is scrubbed the way the sibling `stack` field already was. The bundled snippet's `unhandledrejection` handler `JSON.stringify`s the rejection value into `message`, so a rejected API response carrying an `api_key` reached the backend in full while the same text inside `stack` was redacted
- MCP tool output no longer interpolates error text into the calling agent's context raw. Error messages originate with unauthenticated end users of the monitored application — the JavaScript error endpoint accepts an arbitrary 2000-character `message`, and PHP exception messages routinely embed request input — and the same MCP server registers destructive tools (bulk delete, resolve/ignore, note writes), so planted text could be read as instructions during routine triage. `latest-errors`, `search-errors` and `get-error` now render untrusted scalars as single-line JSON string literals, wrap the stack trace, context, request and user blocks in a fence longer than any backtick run they contain (so an embedded fence cannot close the block early), and state in the result that the values are untrusted data
- The analytics `excluded_paths` check and the per-IP capture throttle now read the **decoded** request path. Laravel's router matches on the rawurldecoded path, so `/%61dmin/users` reaches the `admin` handler while `$request->path()` still reported `%61dmin/users`: excluded pages were captured and shipped anyway, and the throttle keyed on the request line rather than the page, giving one URL an unlimited supply of buckets and so an unlimited number of captures from a single IP. `excluded_paths` entries are also matched case-insensitively now, which can only exclude more from analytics, never less
- Path redaction now reaches **relative** URLs inside breadcrumbs and log context. A relative reference was resolved by the browser against the page it was on, which is one of this application's, so it describes our routes by definition — the fetch and XHR breadcrumb hooks record whatever argument the app passed, which is frequently `/password/reset/{token}` rather than the absolute href. `RouteSecretResolver::forUrl()` previously refused every host-less URL alongside genuinely foreign ones; it now refuses only foreign hosts and host-less URLs carrying a non-http scheme (`mailto:`, `data:`). The candidate routes are resolved once per scrub and threaded through, so a payload with many URL-shaped values walks the route table once rather than once per value. The path boundary is located by matching an authority **anchored at the start** of the string, so a relative URL that carries an unencoded absolute URL in its query or fragment (`/reset-password/{token}?next=https://app.test/dashboard`) is redacted like any other — an unanchored search for `://` used to put the "path" inside the query, leaving the live token in the real path uninspected. Protocol-relative URLs (`//app.test/…`) are covered by the same match
- A URL's **fragment** is scrubbed alongside its query and path. The OAuth implicit flow returns its grant as `#access_token=…&expires_in=…` and never puts it in the query, so a URL with no query at all could carry a live token past redaction; a client-side router likewise keeps its whole route in the fragment, putting the secret in `/app#/reset/{token}` where the server-side path is merely `/app`. A query-shaped fragment (the same strict run-of-`key=value`-pairs test used elsewhere) now goes through the same pair-by-pair redaction, and the fragment is matched segment by segment against the request's sensitive route values. A fragment that is neither shape is returned byte-for-byte
- `SecretScrubber::scrubString()` fails closed when PCRE gives up. `preg_replace_callback()` returns null on an exhausted backtrack or recursion limit, and the previous fallback returned the ORIGINAL string — unscrubbed — to a caller that believed it had been scrubbed, precisely on the long pathological inputs most likely to hold a dumped secret. The whole value is now replaced with `[REDACTED]`, and the give-up is logged to `ranetrace_internal` with the PCRE error so it is never silent
- Captured items are held to a per-item byte budget in the job layer, not only by each capture path's own validation. A single item above the budget is sent anyway (the batch trimmer always keeps at least one), draws a 413, and takes the whole batch of up to 1000 items with it while pausing that type for 15 minutes; a missing length rule on any one capture path should not be able to cause that. Oversize free-form strings are cut and oversize sub-arrays replaced wholesale (truncating a structure mid-way yields invalid JSON). An item still over budget after both is **dropped** and logged to `ranetrace_internal`: every item type has an allow-listed set of fields, so a placeholder marker item would fail the backend's strict field matching and 422 the whole batch — the very failure the budget exists to prevent
- The remaining MCP formatters neutralize untrusted values the way the error tools already did: `error-stats` top-error messages, and the note `body` and `author_name` in `get-note`, `create-note`, `update-note` and `list-notes`. Note content is developer-authored rather than end-user-authored, so this is defence in depth rather than a live path, but it means every string the MCP server hands an agent is now either server-generated or explicitly framed as data
- The JavaScript error endpoint's `timestamp` and `breadcrumbs.*.timestamp` fields are capped at 64 characters. They had no length rule and nothing downstream bounded them, so an unauthenticated client could buffer an item limited only by `post_max_size` — large enough to draw a 413 that discards the whole batch (up to 1000 legitimate errors) and pauses JavaScript error capture for 15 minutes
